## B) خريطة المعمارية (مسارات الاستدعاء)

```
[Boot] server/index.js
  ├─ middleware: أمن الترويسات → Cache-Control:no-store على /api → حدود الجسم (1MB/10MB)
  ├─ مسارات مبكّرة: /healthz · /readyz · /api/health/deep · /api/shadow/report
  ├─ marketStreams.start()      ← ws اختياري؛ بدونه REST seeding/polling
  ├─ liquidity zones + workbench + live-opportunities + strategy2 (بعد تأخيرات 20–95 ث)
  ├─ liveOpportunityRecovery.start(75s)
  │     └─ readAllPages(lifecycle 24h) + readAllPages(opportunities) + calibration + pause
  │        └─ فشل أي منها ⇒ state='failed' ⇒ retry أُسّي 30s→5m ⇒ المحرك لا يبدأ
  └─ jobs دورية: detection 5m · zoneNotify 30s · backtest loop 30s · retention 12h
                  health sample 5m · storage 10m · sync/research/barcode

[Request] → Express route → db.rest (Supabase REST, 20s timeout) → JSON
[Opportunity] zones → scanner(gates) → tracker(state machine) → canPublish → persist + broadcast
[Restart] recovery → rehydrate → engine.start()  (لا نشر قبل state='ready')
```

**نقاط الاعتماد الوحيدة (SPOF) كما رُصدت:** Supabase REST (كل الحالة الدائمة)،
Binance REST (كل بيانات السوق عند غياب البث)، وعملية Node واحدة (كل المحركات في خيط واحد).

## C) سجل المشكلات

### AUD-001 — فحص الصحة يُسقط نفسه (P1)

**الدليل المحلي:** `server/health.mjs` — `containerLimits()` كانت تقرأ
`/sys/fs/cgroup/cpu.max` بـ`readFileSync` **بلا `try`** بينما تقرأ `memory.max` داخل `try`.
الدالة تُستدعى من `snapshot()` في مسارين: البناء الأولي للسقف، وكل لقطة صحة.

**السبب الجذري:** افتراض أن وجود `memory.max` يستلزم وجود `cpu.max`. في cgroup v2 لا
يُنشأ ملف كنترولر CPU إلا إذا كان الكنترولر مُفعّلاً للحاوية.

**الأثر عند الشرط:** استثناء `ENOENT` من داخل `snapshot()` ⇒ `GET /api/health/deep` يرمي
500، وكل عيّنة صحة دورية تفشل (الخطأ مُلتقط هناك فيتحول إلى `persistFailures++` المتزايد
أبداً). أي أن أداة المراقبة تصبح مصدر ضجيج دائم بدل دليل.

**الإصلاح:** تصدير `readContainerLimits({ readFile })` قابل للحقن، وحماية قراءة `cpu.max`
داخل `try` مستقلة. الذاكرة تبقى مقيسة، وغياب حصة CPU يعطي `cpuCores: null` لا استثناء.
**الملف:** `server/health.mjs` · **الاختبار:** `server/tests/containerLimits.test.mjs` (8 حالات).

### AUD-002 — الجاهزية لم تكن تقيس الجاهزية (P1)

**الدليل المحلي:**
- `server/index.js` — `/healthz` تعيد `{ok:true}` دائماً.
- `/readyz` كانت تفحص `fs.existsSync(client/dist/index.html)` فقط.
- `railway.json` — `healthcheckPath: "/healthz"`.
- `DEPLOY.md` §7 يوثّق أن `/healthz` «بلا فحص DB».

**السبب الجذري:** خلط بين liveness وreadiness. النتيجة سلوكياً: عملية فشلت استعادة فرصها
الحية (فلا محرك يعمل) أو بلا قاعدة بيانات مضبوطة تُعتبر «سليمة» عند المنصة وعند أي مراقب
يعتمد على `/readyz`.

**الأثر:** تدهور صامت — وهو النمط الذي تتجنّبه بقية الكودبيس بصرامة (`recovery.state`،
`persistFailures`، `stalled` في المحركات).

**البدائل التي دُرست:**

| البديل | صحة | أثر على النشر | قرار |
|---|---|---|---|
| جعل `/healthz` صارمة | عالٍ | خطر حلقة إعادة تشغيل عند تعطّل DB (Railway يقتل الحاوية) | مرفوض |
| إبقاء `/readyz` كما هي + توثيق | صفر | لا شيء | مرفوض (لا يعالج شيئاً) |
| **توسيع `/readyz` بمنطق جاهزية نقي + إبقاء `/healthz` liveness** | عالٍ | صفر (Railway لا يستخدم `/readyz`) | **مُختار** |
| إضافة خدمة مراقبة خارجية | عالٍ | تكلفة + اعتمادية جديدة | مرفوض (خارج النطاق) |

**الإصلاح:** `server/readiness.mjs` — دالة نقية `evaluateReadiness()` تُصنّف الحالة إلى
`ready | starting | degraded | failed`، وتفصل:
- **حرج (503):** غياب حزمة الواجهة، تخزين غير مضبوط، فشل استعادة الفرص الحية.
- **تحذير (200 + degraded):** بث غير متاح (مسار REST مشروع)، بث غير متصل، تقادم أسعار،
  فشل حفظ سابق.
- **starting (503):** الاستعادة قيد التنفيذ — لا تُعلن الجاهزية قبل اكتمالها.

**التحقق العملي (تشغيل حقيقي محلي، `LIGHT_MODE=1`، بلا Supabase):**

```
GET /healthz → 200 {"ok":true,"up":...}
GET /readyz  → 503
{"ready":false,"state":"failed",
 "reasons":[{"code":"bundle_missing","severity":"critical"},
            {"code":"storage_unconfigured","severity":"critical"},
            {"code":"persist_failures","severity":"warning"},
            {"code":"market_stream_unavailable","severity":"warning"}]}
```

قبل الإصلاح كانت نفس البيئة تعيد `{"ok":true,"dist":false}` بلا أي سبب.

### AUD-003 — ثغرات في اعتماديات الإنتاج (P0/P1)

**الدليل المحلي (`npm audit --omit=dev` قبل الإصلاح):**

| الحزمة | النسخة | الثغرة | الخطورة |
|---|---|---|---|
| `body-parser` | 2.3.0 | GHSA-27r3-jxmh-p828 / CVE-2026-111181 — DoS عبر بايتات زائدة بعد جسم مضغوط | High (CVSS 7.5) |
| `proxy-addr` | 2.0.7 | GHSA-jqcg-44mw-7w3h / CVE-2026-90711 — انتحال IP عبر شبكة ثقة IPv4-mapped IPv6 | Critical (CVSS 9.1) |
| `qs` | 6.16.0 | GHSA-6pq8-jhm2-2vcw — TypeError غير مُلتقط في `stringify` | Moderate |

**تحقق شروط الاستغلال (لا التصنيف الأعمى):**
- **body-parser:** يُستغل قبل التوجيه، بلا مصادقة. التطبيق يستخدم `express.json()` عالمياً
  بلا `inflate:false` ⇒ الشرط **مطابق**. محاولة إعادة إنتاج محلية (بايتات زائدة بأربع
  صيغ) أنتجت أخطاء فك الضغط (`incorrect header check`, `unexpected end of file`) في stderr
  لكن **لم تُسقط العملية**؛ لذلك لا يُدّعى إثبات الاستغلال، بل يُعتمد أن الشرط مطابق
  والترقيع رسمي.
- **proxy-addr:** يُستغل فقط عند ضبط `trust proxy` بصيغة IPv4-mapped/qated. البحث في
  `server/index.js` عن `trust proxy` و`req.ip` ⇒ **لا نتائج**. الأثر هنا **غير قابل
  للاستغلال**، لكن الترقية أُخذت كنظافة اعتماديات.
- **qs:** مسار `qs.stringify` غير مستخدم مباشرة؛ أُخذت الترقية احتياطاً.

**الإصلاح:** ترقية داخل النطاق الدلالي لـ`express@5.2.1` بلا تغيير كود:
`body-parser 2.3.0 → 2.4.0`، `qs 6.16.0 → 6.17.0`، `proxy-addr 2.0.7 → 2.0.8`.
**النتيجة:** `npm audit` = **0 vulnerabilities** في الجذر والخادم والعميل (إنتاج وتطوير).

### AUD-004 — تحذير إقلاع مضلّل (P2)

**الدليل:** `server/index.js` (قبل): `using baked-in Supabase defaults`. `server/db.js`
يقرأ `process.env.SUPABASE_URL || ''` — **لا قيم مدمجة**. عند غياب المتغيّرات لا يوجد
«احتياطي» بل فشل كل نداءات `/rest/v1` برسالة `Failed to parse URL from /rest/v1/...`.

**الأثر:** مشغّل يقرأ السجل يفهم أن النظام يعمل بقيم افتراضية، بينما هو معطّل التخزين.

**الإصلاح:** نص صريح يذكر أن التخزين والاستعادة معطّلان وأن `/readyz` ستُعيد 503.
**تحقق:** ظهر النص في تشغيل حقيقي، وظهر معه `persist_failures` في `/readyz`.

### AUD-005 — وضع النقل غير معلن في الحالة المقيسة (P2)

**الدليل:** `marketStreams.stats()` كانت تُرجع `connected` فقط. عند غياب `ws` يكون
`connected:false` أبداً، فلا يمكن التمييز بين «لا إشارات لأن السوق هادئ» و«لا يوجد بث
إطلاقاً». (`marketStreamsAvailable()` معرّفة في `streams.mjs` لكنها غير مستخدمة.)

**الإصلاح:** إضافة `available` و`transport: 'ws' | 'rest-fallback'` إلى `stats()`، وربطها
بمدخلات `/readyz` (`market_stream_unavailable`).
**لم يُغيَّر السلوك:** البث ما زال اختيارياً كما صُمم.

### AUD-008 — نموذج الثقة مفتوح بالكامل (P1 — مفتوح)

**الدليل:** `server/migrations/000_full_schema.sql` — كل جدول: `ENABLE ROW LEVEL SECURITY`
ثم `CREATE POLICY "<table>_all" ... TO anon USING (true) WITH CHECK (true)`. وكذلك
`010_liquidity_workbench_anon_write.sql` و`013_..._anon_write_convention.sql`.
`server/db.js` يستخدم `SUPABASE_ANON_KEY` **وحده** للقراءة والكتابة.

**السبب الجذري:** قرار تصميمي موثّق في `db.js`: «منصة النشر المُدارة لا تتيح مفتاح
service-role، والجداول بيانات سوق آلية بلا بيانات مستخدمين».

**الأثر (مُصحَّح بعد التحقق):** الواجهة **لا تتصل بـSupabase مباشرة** —
`client/src/lib/api.ts` يثبّت `useSupabase = false` وكل النداءات تمرّ عبر Express. لذلك
مفتاح `anon` يبقى في بيئة الخادم ولا يُضمَّن في الحزمة (تحقّق: لا `VITE_SUPABASE_*` في
أي نداء بناء، ولا استخدام لـ`supabase.from` خارج المحوّل الميت).
السطح المفتوح فعلياً هو **واجهة API نفسها**: 87 مساراً بلا مصادقة، بعضها كتابة وحذف، بلا
حدّ معدل. ومن يملك المفتاح (لو سُرّب أو ضُبط كـ`VITE_`) يستطيع تجاوز التطبيق كلياً
والكتابة على كل الجداول مباشرة.

**لماذا لم يُصلح الآن:** الإصلاح يغيّر نموذج الثقة في الإنتاج ويحتاج سرّاً جديداً
(`service_role`) وترحيلاً على قاعدة حية — وكلاهما خارج التفويض (§3.2). الخطة الكاملة
والترتيب والتراجع في [`security-hardening.md`](security-hardening.md).

### AUD-009 — تغطية `LIGHT_MODE` (P2 — مفتوح)

**الدليل:** `server/index.js` — `LIGHT_MODE` يوقف 4 أنظمة (workbench، بث السوق، الفرص
الحية، استراتيجيتي) لكنه لا يوقف: حلقة الباك تيست (`runBacktestLoop` تُعيد جدولة نفسها كل
30 ثانية)، `periodicDetection`، `zoneNotify`، `runLiquidityLoops`،
`runLiquidityFallbackScan`، و`periodicSync/Research/Barcode`.

**لماذا لم يُغيَّر السلوك:** `periodicDetection` هي مصدر المناطق الذي تعرضه الشاشات؛
إيقافها في الوضع الخفيف يُفرغ الواجهة — أي أن «الوضع الخفيف» يبدو مقصوداً كـ«بلا محركات
قرار» لا «بلا عمل». تغييره يحتاج تحديد نيّة المالك. البند المسجَّل: هل `runBacktestLoop`
(الأثقل) يجب أن يتوقف في `LIGHT_MODE`؟

### AUD-010 — (مسحوب) `ws` مفقود ⇒ تدهور صامت

**التقييم السابق:** «`ws` غير مثبت والمحرك يفشل بصمت». **التحقق الحالي:**
`streams.mjs:924` يسجّل `[market-streams] ws unavailable → REST seeding/polling only`،
و`index.js` يسجّل `[ws] ws package unavailable → running HTTP-only (polling fallback)`
— وقد ظهر السجلان فعلاً في تشغيل محلي. والاختيارية موثّقة في رأس الملف (سطور 19–20).
**الخلاصة:** التدهور معلن لا صامت؛ ما كان ناقصاً هو ظهوره في الحالة المقيسة، وقد عولج في
AUD-005. **لم تُضف حزمة `ws`** لأن تفعيل البث في الإنتاج تغيير سلوكي يحتاج قياس أثر على
سقف الـheap (640MB) قبل اعتماده.

### AUD-012 — اعتمادية ثقيلة ميتة في حزمة العميل (P2)

**الدليل:** `client/src/lib/api.ts` — `createClient(...)` كان يُنفَّذ **دائماً** عند تحميل
الوحدة، بينما `const useSupabase = false` يعني أن مسار SDK ميت تماماً وكل النداءات تمرّ
عبر Express (`restApi`). نتيجة البناء قبل الإصلاح:

```
dist/assets/vendor-supabase-BuOkAX9i.js   220.91 kB │ gzip: 57.39 kB
```

الحزمة تُسحب في مسار التحميل الأول لأن `api.ts` يُستورد من `store` الذي يُستورد من
`App` — أي أن كل زائر يحمّل SDK كاملاً لا يُستخدم أبداً.

**السبب الجذري:** الفصل الصحيح مطبَّق في المنطق (`useSupabase ? sbApi : restApi`) لكن
الأثر الجانبي لإنشاء العميل خارج أي شرط، فلا يستطيع المجمّع إسقاطه.

**الإصلاح:** نقل `createClient` داخل نفس الشرط:

```ts
const useSupabase = false;
export const supabase = (useSupabase
  ? createClient(envUrl || window.location.origin, envKey || 'verdent-baas-proxy')
  : null) as unknown as SupabaseClient;
```

**القياس بعد الإصلاح (نفس الأمر والبيئة):**

| المقياس | قبل | بعد | الفرق |
|---|---|---|---|
| `vendor-supabase` | 220.91 kB / 57.39 kB gzip | **غير مُصدَّرة** | −100% |
| `index-*.js` | 127.67 / 39.98 | 127.50 / 39.93 | −0.17 kB |
| زمن البناء | 3.27s | 3.08s | −0.19s |

**تحقق السلامة:** `tsc -b` ناجح، والبناء ناجح، ولم يُستخدم التصدير `supabase` في أي ملف
آخر (تحقّق بـgrep على `client/src`). لا تغيير سلوكي لأن `useSupabase` ثابت `false`.

### AUD-013 — الاختبارات لا تعمل على نسخة الإنتاج (P1)

**السبب الجذري:** `server/net/limiter.mjs:99` يستدعي `pumpTimer.unref?.()`، و

حيّة. لكن الاختبار الذي ينتظر وعداً يُحلّ بواسطة ذلك المؤقّت يترك حلقة الأحداث بلا أي

السلوك فمرّ الاختبار — أي أن النجاح المحلي كان يعتمد على نسخة أعلى من نسخة الإنتاج.

**إعادة الإنتاج محلياً (قياس قاطع):** نُزّلت Node 22.23.4 المحمولة وشُغّل الملفّان:

| البديل | صحة | أثر | قرار |

### AUD-014 — الجاهزية كانت fail-open (P1)

**كيف اكتُشف:** مراجعة عدائية مستقلة بعد الدفع. السطر كان:

```js
try { probe = runtime.readinessProbe() ?? {}; } catch (e) { probeError = ...; }
const report = evaluateReadiness({ dist, ...probe });
res.status(report.ready ? 200 : 503);      // probeError غير مُستخدَم في القرار
```

**السبب الجذري:** `probe = {}` مع `dist:true` يُنتج `degraded`/`ready:true` ⇒ **200**. أي أن
نقطة الجاهزية تُعلن «جاهز» بالضبط عندما تعجز عن التقييم. والأسوأ: القيمة الافتراضية كانت
`readinessProbe: () => ({})` — أي أن أي إعادة ترتيب للإقلاع (أو entrypoint يستورد `app`
قبل نهاية تقييم الوحدة) تعطي 200 صامتاً بلا أي إشارة.

**الإصلاح:**
- `readinessProbe` الافتراضي **يرمي** (`'readiness probe not initialized'`) ⇒ يفشل مغلقاً.
- قرار الحالة: `const ok = !probeError && report.ready;` و`ready: report.ready && !probeError`.
- `evaluateReadiness({ ...probe, dist })` بدل `{ dist, ...probe }` حتى لا يتجاوز الـprobe
  حزمة الواجهة لو تغيّر شكله لاحقاً.

**الثمن:** لا شيء — المسار الطبيعي (probe مسنَد قبل `listen`) لم يتغيّر؛ تحقّق بتشغيل حقيقي.
